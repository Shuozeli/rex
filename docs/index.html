rex · Page to JSON

Click once on the article you're reading and get it back as clean, structured JSON. Every record conforms to a typed proto schema (Article, Feed, …). The extension doesn't contain the know-how for each site. It downloads recipes (plain data, never code) from a hosted, signed bundle, so new sites and fixes arrive without an extension update.

2Why recipes must be data, not code

Chrome extensions (Manifest V3) may not download code and run it. That's why the existing myfeed recipes can't simply be moved into the extension. rex recipes are only selectors, typed sources and a closed set of transforms, which the packaged engine reads.

myfeed recipe

YAML with an embedded JavaScript function
steps:
  - goto: "https://www.wsj.com"
  - eval:
      ref: extract_articles
scripts:
  extract_articles: |
    (async () => {
      document.querySelectorAll('h3 a')
      ... arbitrary JS ...
    })()
BLOCKED
remote code · MV3
Fetching this from a server and running it breaks the Chrome Web Store rule against remotely hosted code. It would also let whoever controls the server run code on every page you open.

rex recipe (ExtractionRecipe)

Declarative: field path → ordered candidates → typed value
id: wsj.com/main
schema: rex.schema.article.v1.Article
extends: generic/article.v1
fields:
  - path: title
    candidates: [ { css: { selector: "h1" } } ]
  - path: body_html
    expect: true
    candidates:
      - css: { selector: "section.article-body",
               take: TAKE_HTML }
ALLOWED
inert data
The packaged rex engine interprets this. A bad recipe can produce wrong fields, but it can never run code. CI, the CLI and any app embedding rex run the same engine, so they produce byte-identical JSON.

5Which recipe applies? Stage 1: the URL

Matching happens locally against the signed index, so the URL is never sent anywhere. This playground is stage 1 (URL rules). Stage 2 then confirms each URL candidate on the parsed page (JSON-LD type, og:type, selectors); if nothing is confirmed, the schema.org fallback maps the page’s JSON-LD @type to a schema and runs its generic recipe.

Tie-break order (after stage-2 confirmation): exact host beats *. wildcard → a matched include path beats none → higher priority → recipe id. www. is treated as an alias for the bare host.

6How recipes update, and why you can trust them

Every 6 hours (or when you click Refresh), the extension pulls the bundle from Cloudflare. A new bundle is all-or-nothing: if any check fails, the old bundle stays active. Try to break it.

    7Why download all recipes instead of just the one you need?

    Fetching recipes one site at a time would tell the CDN which sites you read. Syncing the whole bundle reveals nothing about your reading. Recipes are small (a few KB each), so this is cheap.

    8"Dynamic schema": what changes, how often, and how

    There are four layers. Only engine features and the bundle format need an extension release. Even a contract change is handled with a version flag, so older extensions keep working.

    Recipe content

    changes: continuously
    New sites and selector fixes are a reviewed PR with fixtures; merge publishes a new immutable recipe version. Your extension picks it up on the next sync. No release.

    New schemas

    changes: per recipe
    A new page type (e.g. product.v1) is a new annotated proto message, shipped in the bundle’s descriptor set with a generic recipe. Still typed and schema.org-bound, never a key-value bag. No release.

    Contract (rex.extract.v1 → v2)

    changes: rarely
    Additive proto changes are safe. New engine capabilities are gated by a recipe’s requires flags: an older extension skips that recipe and falls back instead of misbehaving. Breaking changes get a new package.

    Bundle format

    changes: almost never
    The format lives under the /v1/ path. A breaking change ships at /v2/ while /v1/ keeps serving older extensions.
